# Agent Note: Durable SDK attempts

Status: implemented

English | [中文](2026-08-14-durable-sdk-attempts.zh.md)

## Problem

The SDK `session/prompt` operation accepted a prompt and returned only a process-local message id. An external workflow operator could durably record an execution intent before calling the Harness, but it could not bind that intent to a durable Harness fact. If either process lost the response, the operator could not distinguish an unreceived prompt from a queued, running, or terminal turn. Retrying could create a second turn and repeat tool effects; refusing every retry could strand work that had never reached the Harness. Process-local client history did not repair this ambiguity after restart.

## Decision

The JSON-RPC SDK exposes a separate durable-attempt contract beside the legacy prompt operation: `session/attempt.start`, `session/attempt.get`, and `session/attempt.cancel`. An attempt is identified by the exact tuple of session id, bounded caller attempt id, lowercase SHA-256 input fingerprint, and server-derived deterministic message id. `start` accepts content blocks and returns a queued, running, or terminal receipt plus a deduplication flag. Repeating the same identity and content observes the existing attempt; reusing the attempt id with a different fingerprint or content fails closed.

The attempt identity is stored in the source of the same durable user message inserted by `agent/inbox/spliced`. The server flushes that insertion before allowing dispatch, rather than appending a second attempt record that could diverge from the inbox fact. Lookup reconstructs receipts from the live session or the persisted session log: the inbox projection identifies queued work, the claimed user message binds a turn, and `turn/end` supplies the terminal reason. A terminal receipt also carries the claimed turn, terminal event sequence, and final assistant text. Session operations are serialized so start, lookup, cancellation, and shutdown cannot publish contradictory receipts.

Every persisted SDK session managed through an ownership-capable backend has one backend-enforced writer owner. The server acquires ownership before create, resume, or wake, retains it through quiescence, final flush, and agent disposal, and then releases it. First-party persistence providers declare this capability and use crash-released native advisory locks with durable fencing generations, so another process cannot resume and claim the same queued attempt concurrently. Legacy prompts and read-only attempt lookup remain available with backends that do not declare ownership, but attempt start and cancellation reject them; ownership contention or loss also fails closed. After an SDK attempt is claimed, an `agent/pre-step` listener durably flushes the claimed turn and user-message intent before delegating to model dispatch; this barrier is independent of optional checkpoint-policy composition.

Resuming a persisted agent can opt into `wakePending`. The concrete loop publishes the reconstructed agent and its listeners first, then wakes the driver only when its durable inbox already contains work. This creates no new message and therefore lets a caller safely redrive the same attempt after a crash between durable enqueue and dispatch. Legacy resume behavior remains non-waking unless the caller requests this option.

Cancellation is identity-bound. A queued attempt removes exactly its durable message and returns a canceled terminal receipt. A running attempt requests cooperative user cancellation, preserves unrelated inbox work, waits for quiescence, flushes, and then returns the reconstructed terminal receipt. An absent, foreign, or already-uncancellable attempt fails instead of reporting a local cancellation that the session log cannot prove.

Cancellation causes cross an untrusted runtime boundary before they become session facts. Some runtimes mutate an object-valued `AbortSignal.reason` (Node's HTTP client can add a non-enumerable `stack` accessor), which would make strict JSON persistence reject a later `turn/end`. The agent loop therefore snapshots the closed `AgentCancelCause` union into a fresh JSON-only record immediately before durable append; it never persists the object reference that an adapter or tool observed.

The TypeScript and Python clients expose the three low-level operations and high-level run/get/cancel methods. High-level durable runs validate every returned identity and poll exact attempt lookup every second until a 300-second overall deadline by default; idle notifications only accelerate a poll. A client timeout stops waiting and never cancels the runtime-owned attempt. The final result comes from the exact terminal receipt rather than a global idle observation alone. The legacy prompt API remains available and retains its previous wire shape.

Initialization also exposes a strict schema-2 runtime-binding envelope containing protocol version, schema version, a path-free canonical lowercase persistence-instance UUIDv4, and `rootConfigSha256`. JSONL atomically stores the UUID in the root identity file; SQLite reuses its immutable singleton store id; the SDK server rejects any backend value outside that wire-safe UUID form without echoing it. App boot reads the resolved root Cordis file once, hashes those exact bytes, and mounts content decoded from the same capture without letting Loader reopen the path. Before initial child apply, pinned boot pre-imports each effectively enabled plugin, recognizes Include and Group identities across aliases and built-module copies, rejects statically named Includes even when disabled, rejects every effectively enabled Include identity, and applies Loader-equivalent disabled propagation so disabled alias modules are not imported. An inherited pre-apply policy prevents programmatic or later activation of an Include; the root Include config is immutable and its child tree seals after initial mount. The digest itself is a non-enumerable capability confined to that subtree, so a removed or replaced root cannot lend stale authority to a sibling SDK server. Enabled plugin modules can still run top-level module code during preflight. Every durable receipt repeats the envelope. Both SDKs pin the first binding, atomically restart a subprocess that dies after initialization, reinitialize without dispatching a prompt, and reject a replacement or receipt bound to another store or root digest. `rootConfigSha256` proves only the mounted root file bytes and is not a semantic plugin-graph fingerprint: startup patch arguments, environment-derived expression values, plugin module bytes, credentials resolved outside that file, and plugin external state remain outside the binding. An operator that needs those inputs fenced owns a separate authoritative manifest or digest.

The Python SDK can atomically pair that binding with an opaque live-subprocess generation before an operator validates configuration. A run fenced by the captured generation uses the exact existing client for subscription, attempt admission, and terminal polling. It does not start or replace a process: a dead or different generation fails before `session/attempt.start`. Unfenced lookup retains automatic restart so recovery can inspect durable state through a replacement child.

The persistence UUID identifies a logical store lineage, not one physical replica, a fresh snapshot, or an anti-rollback generation. Copying a complete JSONL root or SQLite database preserves that value by design, while the copied per-session ownership locks protect different physical files. The original and copy must therefore never serve durable attempts concurrently. An independent clone requires an offline provider-specific rekey followed by a single-active cutover; rekeying changes the binding but does not make replaying duplicated attempt history concurrently safe. No public online rekey seam or SDK-server clone mode exists because neither can prove that every physical replica is quiescent. The operator owns that deployment fence.

Crash repair may close a claimed open turn with `interrupted`. This proves that the exact attempt was claimed and did not record a normal Harness completion; it does not prove that an external tool effect did or did not occur. An operator retains its recovery fence and reconciles the exact attempt and any tool idempotency evidence instead of interpreting `interrupted` as cancellation or automatically retrying the effect.

## Alternatives considered

Adding optional attempt fields to `session/prompt` was rejected because an older server could ignore them while appearing to accept a durable request. Writing a separate attempt event before or after inbox insertion was rejected because a crash between the two writes would recreate the dual-write ambiguity. Keeping attempt receipts only in the SDK client was rejected because process loss erases the evidence needed for reconciliation. A process-local session mutex was rejected because two server processes could still resume and dispatch the same persisted inbox. Automatically retrying an unmatched tool call was rejected because execution may already have reached an external side effect.

Using an operating-system process id as the dispatch fence was rejected because ids are reusable and expose a platform-specific implementation detail. Automatically restarting a dead child for a generation-fenced run was rejected because the replacement may have loaded changed provider or Loader configuration after the operator validated the previous child.

## Consequences

An operator such as WTB can persist an attempt fence, call the Harness with the same identity, and after either process restarts query or redrive that exact attempt without creating a second Harness turn. A queued attempt survives restart and is woken once by its exclusive owner; a completed attempt is returned from durable evidence; identity conflicts, ownership contention, and unprovable cancellation fail closed. Tests cover duplicate start, conflicting replay, queued and running cancellation, persisted terminal lookup, restart wake and crash repair, cross-context ownership, pre-dispatch insertion and claim flushes, shutdown release ordering, same-capture root hashing and mounting across path replacement, nested Include aliases and disabled preflight semantics, actual pre-apply identity enforcement, immutable Include config and sealed child mutation, subtree-scoped digest withdrawal, adversarial persistence identities, real Loader composition, and both SDK clients' wire validation.

This contract provides effect-once admission for a Harness turn, not a distributed transaction. The WTB database, Harness session log, and an arbitrary external tool cannot commit atomically. A tool provider that supports idempotency can receive the stable tool call id, and an unmatched durable tool call remains `TOOL_OUTCOME_UNKNOWN` under the [semantic checkpoint policy](../bug-fix/2026-07-21-semantic-session-checkpoints.md); the Harness does not claim generic exactly-once external effects.

A generation fence deliberately gives up transparent liveness for first dispatch: if the validated child exits, the operator must re-establish and revalidate a process binding before attempting admission. Durable lookup remains restartable because it does not create an attempt or wake non-terminal work.

The runtime binding likewise provides no freshness or anti-rollback proof. Restoring an older store snapshot or running a copied lineage under another physical path can present the same binding; operators must fence backup restore, replica promotion, and clone cutover outside the Harness.
